# P4A graphical subgoal evidence

## Status and authority

P4A is the first graphical human-review surface for CCSolver reasoning. It turns
checked P3 contextual-witness boundaries into deterministic semantic SVG panels
and a static HTML comparison without replaying the engine or inferring hidden
map layers. The checked P4A files are preview artifacts, not frozen root
protocol schemas. They are authoritative for this characterization only after
`npm run ccsolver:p4a:check` reproduces every generated byte.

Human review is durable input rather than generated output. Review sidecars are
bound to exact machine-evidence and witness content references and are never
silently overwritten by regeneration.

## Big-plan position

```text
P0/P1 static facts and topology
              |
P2A exact runtime perception
              |
P3A terminal-first theory
              |
P3B exact leaf witness
              |
P4A graphical evidence      <--- delivered here
              |
P5 continuous full-level replay and certification
```

P4A answers: “Can a person inspect what one proposed subgoal meant, what exact
state was observed before and after it, and how a failed attempt differs from
its intended ending?” It does not answer whether Key Pyramid is solved or
whether multiple witnesses compose through one continuous run. P5 owns those
claims.

## Pure evidence contract

`@tworld/ccsolver/render` is a pure layer. A `SubgoalEvidenceViewV1` binds the
target, normalized level identity, LevelFacts, terminal plan, contract, and
witness. Its shape makes these panels mandatory:

- `starting`: an exact observed boundary;
- verified `ending.observed`: an exact observed boundary; or
- failed `ending.expected` and `ending.actual`: a contract-bound intended scene
  beside a separate exact observed stop and first failure.

Every panel uses one fixed bounded viewport, covers every cell in that crop,
retains the supplied semantic item stack literally, and includes a textual
equivalent. Expected scenes never carry forged runtime fingerprints. Cropped
panels are derivative review aids; the full-world P3 witness remains authority.

Overlays retain their evidence basis:

- `regressed-requirement` for a backward prerequisite;
- `backward-candidate` for a retained alternative;
- `plan-intent` for a proposed route or selected target;
- `observed-witness` for exact boundary positions and before/after cell state;
  and
- `donor-evidence` when donor evidence is actually used.

Failure is a status layer, not a sixth evidence basis. Routes are never promoted
from plan intent to observed merely because their endpoints were observed.

## Key Pyramid review result

The static review page is
[`fixtures/golden/p4a/review.html`](../fixtures/golden/p4a/review.html).
It shows the same five-by-five crop, `x13..17`, `y16..20`, `z0`, for MS and
Lynx before and after the placement-bound adjacent-red-key witness.

The panels preserve target-native differences that matter for review:

- MS begins at native tick `-1`, facing west, and verifies at tick `0` after
  one east poll;
- Lynx begins at native tick `-1`, facing south, and verifies at tick `3` after
  east plus three neutral polls;
- both end at `(16,19,0)`, facing east, with red-key inventory `0 -> 1` and ten
  chips remaining; and
- MS and Lynx semantic cell stacks are rendered exactly as supplied. The
  renderer does not invent an underlying floor where MS omitted one.

The selected red key, adjacent blue-key alternative, later red-door
requirement, and one-cell route preview remain separately labeled. The route is
plan intent. Observed evidence consists of exact start/stop positions and
changed-cell boundaries; P3 did not retain intermediate render scenes, so P4A
does not fabricate an animation or continuous observed route.

## Failed canary

The standard-only synthetic failed-red-key view proves the negative review
path. Its intended ending shows Chip on the red-key cell, the key absent, red
inventory one, and two chips remaining. Its actual stop keeps Chip at the start,
keeps the key present, leaves red inventory at zero, and shows one chip
remaining. The page identifies the first `witness.postcondition` failure and
keeps intended and observed states visually and structurally distinct.

The canary uses only the standard semantic vocabulary. It reads no DAT, TWS, or
donor source and introduces no path around the solver-wide rejection of
DATTools-invalid layouts or expanded tile codes `0x70` through `0x75`.

## Durable review state

`ReviewStateV1` is stored outside generated artifacts under
`ccsolver/reviews/p4a/`. It contains:

- `unreviewed | reviewed | changes-requested` status;
- ordered human notes;
- ordered presentation-only overlay overrides; and
- an auditable stale binding with previous/current exact content references.

An unchanged evidence/witness binding preserves the review byte-semantically.
A changed witness sets `changes-requested` with `bound-witness-changed`; an
evidence-only change uses `machine-evidence-changed`. Notes and overrides are
preserved. Review cannot alter evidence basis, geometry, or machine content.

The HTML page resolves machine evidence and review as separate inputs. Review
is not embedded inside the evidence value whose digest it references, avoiding
a content-address cycle.

## Checked outputs and commands

Generated output lives under `ccsolver/fixtures/golden/p4a/`:

- three canonical evidence JSON values: Key Pyramid MS, Key Pyramid Lynx, and
  the failed synthetic canary;
- seven byte-addressed SVG panels;
- `manifest.json`; and
- `review.html`.

The three human-owned review sidecars live under `ccsolver/reviews/p4a/` and are
not generator outputs.

Regenerate machine output intentionally with:

```sh
npm run ccsolver:p4a:generate
```

Verify without writing with:

```sh
npm run ccsolver:p4a:check
```

The runner stages all generated bytes before promotion. The bounded CI gate has
a two-minute timeout. No corpus sweep, headless browser, rasterizer, animation,
or gameplay-engine execution is part of the real Key Pyramid transformation;
P4A consumes checked P3 bytes.

## Next human checkpoint

P5 is the next decisive checkpoint. It must expand the reviewed Key Pyramid
leaf into a complete target-specific subgoal sequence, execute every segment
continuously from canonical initialization to victory, write complete TWS
files, and certify both targets in the TypeScript engines and native oracle.
Only then can a human judge the full route and whether individually credible
pieces actually join.
